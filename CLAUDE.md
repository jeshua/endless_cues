# endless_cues

*For humans: this file is the instructions coding agents (Claude Code, Codex) follow when they work in this repository. To use or build the app, start at [`README.md`](README.md).*

Endless Cues: an open-source, cross-platform show-control app (a QLab alternative), with a paid hosted assistant. [`README.md`](README.md) is the map; [`docs/specs/`](docs/specs/README.md) is how it is meant to work. It grew out of the show app in `endless_forms/visuals/stage-app` (also called "Endless Cues", the one in `/Applications`); **that app is the running show's and is never touched from here.**

## Rules

- **The website and the service are not here.** endlesscues.com (the landing page and the manual), the account site, the reports inbox, the assistant proxy and billing are in the private repo `endless_cues_service`, checked out beside this one (`../endless_cues_service`). The two meet only through [`docs/specs/17-service-protocol.md`](docs/specs/17-service-protocol.md) (a copy of that repo's `PROTOCOL.md`; change both together). What here writes into the site (`node bin/release.js site`, `build/mark.ts`) finds it through `bin/site-dir.ts` (`--site-dir` or `EC_SITE_DIR` to point elsewhere). Never copy service code in here, and never copy GPL code from here into the service.
- **This repo will be public.** Nothing show-specific goes in: no cast or crew names, venue addresses, the show's cue list, IP addresses, or dated anecdotes in comments. `reference/` (the private snapshot the code was ported from) is gitignored and must stay that way; do not copy text out of it.
- **A show changes only through `core/show/ops.ts`.** No code writes to a show document any other way. A new kind of edit is a new operation, with a test. The assistant gets no tool that edits or plays a show.
- **`core/` never requires Electron.** It is tested with `node --test` and fakes (`test/helpers.ts`). If a test needs a window, the logic is in the wrong place.
- **The renderer is a view.** It holds selection and layout, never show state; it sends `cmd`s and draws what it is pushed. Anything that must survive a reload lives in `app/main/host.ts`.
- **TypeScript, strict, one build script.** Edit the `.ts`; the `.js` beside it, and the bundles, are written by `build/compile.mjs` (`npm run build`, `npm run watch`) and never edited or committed. No `any` where a real type can be said, no `@ts-ignore`. A type that two sides share (the host's state and commands, the audio and stage windows' messages, a cue) is declared once and exported ([ADR 0006](docs/adr/0006-typescript.md)).
- **No CDN, no network at runtime** (the assistant excepted, and only when asked; and the daily update check, one GET of the feed in Edit mode with nothing playing, `core/update/updates.ts`, which a test run never makes). Renderer dependencies are vendored in `app/renderer/vendor/`.
- **Simple until asked.** Out of the box it is a plain cue list, on a new show and on an imported one. Anything that analyses, decides or acts by itself (ducking, a stop that fades, a bus that crossfades, a new sound listened to and sorted, tempo finding, a network listener, a module, the assistant) is off until a person turns it on, with one obvious switch; a bus's kind is a label. [`docs/specs/00-defaults.md`](docs/specs/00-defaults.md) lists every such behaviour: add a new one there, off, with a line in `test/defaults.test.ts` (`test/kinds.test.ts`, "a new show plays as a plain cue list", holds the sound's side of it). The tools for steering a running track (the Playing waveform with its bar lines, pause and stop per cue, holding a loop drawn or from here, markers, Skip and Fade to, Quantise, Find the tempo) are the cue list's own.
- **Cue types are one table**, `core/show/cue-types.ts`: validation, the inspector, the assistant's reference, the docs and a cue's TypeScript type (`core/show/cue-fields.ts`, written by `npm run cue-fields`) all come from it. Add a field there, not in five places.
- **Colour carries meaning**: `--go`, `--standby`, `--danger`, `--accent` and nothing else ([`docs/specs/07-design-system.md`](docs/specs/07-design-system.md)).
- **Show settings live in the show file; this computer's settings do not** (output device, assistant sign-in: `config.json` in userData). Never put a credential in a show.
- **The brand is the original app's**: the Lab and Ocean themes, the tabletop and algae photographs, Jost and Bricolage Grotesque were copied from the show app at the owner's request (`app/renderer/{images,fonts}`). They are copies: the show's own files are never edited from here. **The mark is this project's own** (a lopsided infinity sign, a cell dividing, in bone and copper): every logo and icon file is written by `node build/mark.js` and never edited by hand ([`docs/brand.md`](docs/brand.md)).
- **QIRX-G is the assistant's face**: the head of QIRX-G, a robot puppet from the show, drawn flat with its pentagon eye carrying the state (`app/renderer/Qirx.ts`; no photographs). It appears only where [`docs/brand-assistant.md`](docs/brand-assistant.md) lists: the side panel's resident, the assistant's drawer, Settings ▸ Assistant and About, and as a plain sign on the Assistant button; never in a cue row, the inspector, the stage or the web remote. In Show mode it is asleep, dimmed, and nothing of it moves. Its lamp is yellow and yellow means standing by here, so its state is always said in words too, it is low at rest, and its yellows (`--qirx-lamp`, `--qirx-rest`) are never used for anything else. Everything it touches says little: a label and a few words.
- Cross-platform always: `CmdOrCtrl` accelerators, `path` for paths, `keys()` for shortcut labels, no macOS-only API without a guard.

## Checks

```bash
npm test          # must pass before any commit
npm run smoke     # after any change to app/ (offscreen, muted, no ports, never takes focus)
SMOKE_SHOTS=smoke-out npm run smoke    # also saves pictures of the window; look at them after a UI change
```

## "Run the virtual users"

When the owner says **"run the virtual users"** (or "run the usability test"), do this, in order:

1. `pgrep -fl "Endless Cues.app/Contents/MacOS"`. If the show's app is running, say so and stop: two of the five sessions open network ports (`theo`'s 53000 among them; `june`'s talks to a stand-in prop on 53100 and may look for props with a broadcast), and five windows appear on the screen. Run beside it only if the owner says to, and then without `theo` and without `june`.
2. `npm test && npm run smoke`. Do not put users on a build that fails either.
3. `npm run users:prepare -- <run>` (the run name is today's date; add `-b`, `-c` for a second run that day). It prints one `BRIEF.md` per person.
4. Start one subagent per brief, all five in one message so they run together, each with only this prompt: *"Read `<path to BRIEF.md>` and do exactly what it says."* Tell them nothing else: no hints about the app, no list of what changed. The one exception: when the owner has said to run beside the show's app, add a sentence saying so in their words, or the agents see the app running and stop. Wait for all five.
5. `npm run users:collect -- <run>`. If it says a report is not in the agreed shape, send that agent the complaint and collect again.
6. Read `docs/internal/usability/<run>/summary.md`. Reproduce each bug yourself before believing it. Then tell the owner: the five verdicts, what two or more people hit, the blockers and majors, and what you could not reproduce. Each finding that stands becomes a tracker line or a fix.
7. Delete `test/users/runs/<run>/` (about 170 MB) once it is collected.

What the system is: five invented people, each with a show of their own, each an agent that uses the app only through its window (`bin/ec-user.ts`, `app/main/drive.ts`) and writes a report ([`test/users/README.md`](test/users/README.md)). Run it after a change to how the app is used, not on every commit.

The smoke run is safe while the show app is open: its own temp settings folder, no audio device opened at all (`audio.html?silent`), no module started, activation policy `accessory`. Still: never run `npm start` or a packaged build on the show computer during a performance, and remove `dist.noindex/` after a packaging test (a second "Endless Cues.app" on the disk confuses Spotlight).

## Not verified yet

- The native audio engine (`ec-audio`, `native/audio/`; `docs/specs/18-native-audio.md`), off by default: run only `--silent` in the unit tests and the smoke run (it starts, plays a short tone to its end by its path, and hands back to Web Audio), and once on this Mac's built-in speakers by `ec-audio measure` at -40 dB (GO to output 8.8 ms mean, 11.7 ms worst, by the program's own clock). Never on a real interface: its true latency (`ec-audio measure --loopback <input>`, written, never run), a lost device, more than two outputs, Windows (WASAPI) and Linux (ALSA), a packaged and signed build finding it in its resources, and listening to any of it.
- The Endless Cues assistant (the `cloud` provider, `core/assistant/cloud.ts`) against the deployed service: the device flow, a turn, the month's lines and signing out are tested only against a stand-in on 127.0.0.1 and in the smoke run with no network. The service's side was tested against a stand-in model; the models themselves were tried with two direct calls (function calling through the Responses API), not through the Worker.
- The assistant's key-based providers (Anthropic SDK, OpenAI-compatible) against a live service: tested only with scripted providers and a local fake server. The tools and the agent loop ARE verified live, through Claude Code (`.scratch/live-claude.js` shows how). Codex has never been run.
- The device templates in `core/net/devices.ts` against real equipment.
- The lighting-desk and OSC modules against real hardware in this codebase (the Eos messages are the ones the show app uses; the grandMA3 fire message was changed to the manual's `Goto Cue n Sequence l` and has met no desk). The script to follow at a desk is in `docs/specs/14-lighting.md`.
- The app's own lighting (`core/light/`): **no fixture has ever been lit by it.** Art-Net and sACN are tested to the byte against the specifications and on loopback sockets only; no node has received a packet, ArtPoll has met no real node, and timing at 40 Hz has not been measured. `docs/specs/14-lighting.md` has the script for the first time. - OSC control against any remote built for QLab (Bitfocus Companion, the Stream Deck plugin, QLab Remote): OSC over TCP, the 53001 reply port, passcodes with levels, `/new` `/move` `/delete` `/renumber` and the `/listen` event broadcast are written from QLab's manual and tested against themselves on loopback. `docs/specs/06-control-surfaces.md` section 6.6 is the script for trying each. QLab Remote may not connect at all (no Bonjour, no encrypted connection).
- Network cues that are text or hex, a patch's several destinations and its choice of interface: tested on loopback only, never against a projector, a switcher or a computer with two real networks.
- The web remote's faders and Load to Time on a real phone (drawn and driven in an offscreen Chromium window only).
- A Mic cue on a real input (only a stand-in signal in the test run); its latency is unmeasured.
- MIDI against any equipment: the bytes are tested, Web MIDI opens, and no port has ever been sent to. That covers MIDI cues (and their faded values), MIDI File cues, MSC in and out, and MIDI triggers and show commands.
- Timecode against any equipment. MTC out is checked to the byte and by the times its messages are stamped with; whether the computer's MIDI system sends a stamped message at its time (the whole of MTC's steadiness, `docs/specs/06-control-surfaces.md`) has not been measured at a port, on any platform. LTC out has been decoded only by this app's own reader (in the tests, and in the smoke run through the real audio worklets), never by a timecode reader; its level and edge shape are unchecked against one. MTC in and LTC in have heard only what this app made; LTC in has never opened a real input.
- A QLab Timecode cue on import: the field names are from a real file, what they hold is guessed (`timecodeOf` in `core/import/qlab.ts`), as is where a pitch bend's value and a faded MIDI value's end are kept.
- Output routing on a real multi-output interface: checked only on the test run's pretended eight outputs (meters, not ears). That covers a bus's pair, a cue's own outputs (the matrix), files of more than two channels, audition to its own pair and the outputs' trims: none has been heard, and channel order on a real device is unconfirmed.
- A sound file dragged from the desktop onto an Audio cue (to replace its file), and the right-click menu's new items: written; a test run has no desktop to drag from and no screen for a menu (the host command behind the drop is smoke-checked).
- Cut, copy and paste between two shows in the window: run by hand in a test session and unit-tested, not in the smoke run.

- **Sound design (a cue's chain of tools, `core/audio/chain.ts`): nobody has listened to any of it.** Every tool is checked by measurement only: the gate, compressor, crusher and pitch shifter as kernels in the unit tests, and the built chain rendered offline in the audio window by the smoke run (`measure`; `app/main/smoke-sound.ts`).
